# 受控个人智能体系统中的机密隔离、设备同步与反自动化机制

## ——一次短信验证码登录失败的系统性分析

**摘要**
本次事件表面上是"一条短信验证码未能在五分钟有效期内完成填入"，实质上是三套互不隶属的安全机制在同一时序窗口内叠加作用的结果：智能体侧的机密令牌化（credential tokenization）机制、设备侧的异步同步（asynchronous replication）通道、目标站点侧基于行为评分的风险自适应验证（risk-based adaptive authentication）。三者在设计目标上均为正当的纵深防御（defense in depth）措施，但其组合在端到端时延预算（end-to-end latency budget）上不成立，最终构成"局部正确、整体失效"的级联故障（cascading failure）。

## 一、威胁模型与设计目标

个人智能体（personal agent）的特殊性在于，它被授予了对用户数字资产的高权限访问：账号会话、短信、文件、支付工具。由此产生的核心设计张力是：能力（capability）与机密暴露面（secret exposure surface）正相关。为消解这一张力，系统采用了三条原则：

1. **最小权限与机密不可见原则**：智能体的推理层（即"负责思考和说话"的那一层）不得接触机密原文，包括密码、一次性验证码（OTP）、会话令牌。理由是推理层同时是交互层，它的一切输出（回复、日志、记忆文件）都构成潜在的泄露通道（exfiltration channel）。只要原文进入推理层的上下文，它就可能被复述、被持久化、被注入攻击诱导导出。因此机密必须在到达推理层之前被剥离。

2. **能力与数据的分发控制权保留在用户侧**：设备数据不做直连推送，而是由用户设备上的伴随应用（companion app）持有权限、按策略同步。用户可以通过关闭应用、撤销权限即时切断通道，即所谓的"物理熔断"。

3. **执行环境受控且可审计**：网页操作由受控浏览器（controlled browser runtime）执行，而非推理层直接发出任意请求。每个动作留痕、可中断、可回放，以便事后审计与事中干预。

## 二、三个核心机制的实现

### 2.1 机密令牌化与受控注入（Tokenization & Controlled Injection）

当短信到达同步通道时，系统在数据进入推理层之前执行模式识别：被识别为验证码的数字串被替换为一个不透明引用（opaque reference，即短信正文中看到的"凭证编号"，学名 credential reference）。推理层只能观察到事件的元数据——发信号码、时间戳、用途标签——而不能观察到载荷本身。

真正的验证码被保存在推理层之外的凭证保管区（credential store）中，设有短时效。当某个执行步骤（如登录页的验证码输入）需要该机密时，推理层只能提交"引用 + 目标来源（origin）"这一对参数，由运行时（runtime）向用户弹出批准卡（approval card）；用户批准后，运行时将保管区中的原文直接注入目标页面的输入框。整个过程中原文只在"保管区→页面"这一段受控管道中流动，绕开推理层与对话记录。这本质上是支付行业令牌化（如 PCI DSS 场景下的 PAN tokenization）在智能体架构中的移植：用不可逆的引用替代敏感原文，使高权限组件在"可用不可见"的状态下工作。

### 2.2 设备侧异步同步（Asynchronous Replication）

推理层读取到的短信并非手机短信数据库的实时视图，而是伴随应用异步复制（asynchronous replication）产生的副本，其一致性模型是最终一致性（eventual consistency）而非强一致性（strong consistency）。复制通道的存在依赖伴随应用进程存活：应用进程被终止（即用户"划掉后台"的操作），复制即中断，副本冻结在最后一次成功同步的状态；进程恢复后，复制需要重新建立并追赶增量（catch-up replication），追赶完成前，读取结果反映的是陈旧快照（stale snapshot）。

本次事件中，19:27 到达手机的短信，在 19:33 的多次读取中仍未出现在副本里，属于典型的复制延迟（replication lag）叠加增量丢失：消息到达时复制通道处于中断状态，恢复后的追赶过程又未能及时覆盖该条目。

### 2.3 站点侧的风险自适应验证（Risk-Based Adaptive Authentication）

目标站点（Bilibili）的登录链路部署了以极验（Geetest）为代表的行为验证系统。其机制不是简单的"点对即放行"，而是分阶段的综合评分：第一阶段在页面加载与输入期评估环境指纹（environment fingerprinting，包括 navigator.webdriver 标志、Canvas/WebGL 指纹、时序特征）；第二阶段在高价值动作（触发短信网关下行）瞬间，结合点击轨迹的动力学特征（贝塞尔轨迹拟合、按下-释放间隔、动作间熵值）重新评分，评分不足即触发加码验证（step-up challenge）。

受控浏览器作为自动化环境，其行为熵天然低于人类，这解释了实测中的全部现象：偶发一次性通过（轨迹模拟达标时）、顺序点选正确仍判失败（字符识别正确但行为评分不达标时）、以及"通过一道又弹第二道"（分阶段触发）。

## 三、失效分析：时序预算的耗尽

短信验证码的有效期（300 秒）本质上是发码方设定的端到端时序预算（latency budget）。本次链路的环节依次为：发码与下行投递、手机接收、伴随应用复制、推理层读取与引用提取、浏览器定位等待点、用户批准、注入填入。

其中每一环在正常运行时都只需秒级，但在故障时段出现了两个非常规时延源：

- 其一，复制通道中断导致后续全部环节失去输入，第一条验证码（19:01 发出）在通道恢复前（19:19）根本不可见，直接耗尽预算；
- 其二，第二条验证码（19:27 发出）遭遇复制追赶不完全，副本陈旧化，预算再次在等待中耗尽。

与此同时，前置的站点风控又消耗了大量预算：从 16 时至 19 时的多数时间实际消耗在与自适应验证的对抗上——这是一个典型的重试放大（retry amplification）场景：失败触发重试，重试行为本身进一步抬高风险评分，使后续通过率继续下降，形成负反馈回路（negative feedback loop），最终是靠人工总结出的行为整形策略（behavioral shaping：预热停留、动作降速、失败冷却）才打破回路。

## 四、根本矛盾

归结起来，本次失效源于两个结构性矛盾。

**第一，安全机制的串联与可用性目标的冲突。** 每一道机制都在为自己的威胁模型尽职——令牌化防泄露、同步隔离防失控、行为验证防机器人——但三者串联后的复合时延与复合故障率，没有任何一方负责核算。这正是分布式系统设计中经典的"组合爆炸"（composition problem）：安全属性大体可组合，时延与可用性属性不可简单组合。

**第二，智能体的双重身份冲突。** 对站点而言，智能体是需要被识别和防御的自动化程序；对用户而言，它又是持有合法授权的代理人（authorized agent）。现行 Web 的信任基础设施（以 CAPTCHA 为代表）无法区分"恶意自动化"与"授权代理"，只能按行为特征一概拦截。业界正在讨论的出路——如基于密码学的代理授权证明（agent attestation）、站点对合法代理的白名单通道——目前均未落地部署。

## 五、结论与改进方向

就本次具体任务而言，工程上可行的缓解措施有四：

1. 保证复制通道存活，即发码窗口期内保持伴随应用进程不被终止，使复制延迟回到秒级；
2. 将行为整形策略固化为受控浏览器的标准操作规程，降低风控对抗的时间成本；
3. 优先使用不依赖短信通道的认证方式（如已登录 App 的扫码授权），在架构上绕开时序预算最紧的环节；
4. 在链路中预留预算监控，当剩余有效期不足以覆盖预计交接时延时，提前重发而非等待过期。

更一般的结论是：个人智能体的安全架构已经解决了"不可信的强能力组件如何安全地持有机密"的问题，但尚未解决该架构与既有 Web 反自动化基础设施、以及与人类尺度的时间约束（五分钟有效期）之间的兼容性问题。今天下午到晚上的这三个小时，就是这个未解决问题的完整标本。
